## 1. 先纠正目标定义

“形式不限”并不等于桌面端、Web 端和移动端可以同时推进。当前项目是 Wails 桌面应用，主前端通过 Wails 绑定直接调用 Go 方法；将它直接放到静态托管平台并不会自动变成 Web 应用。若当前核心目标是尽快获得一个**可以持续使用**的股票分析软件，第一选择应是修复并交付现有桌面端，而不是先做 Netlify 改造。

这里把第一版“可用”定义为以下可验收结果：

1. Windows 或 macOS 至少有一个平台可以安装、启动、退出并再次启动；
2. 能搜索完整 A 股股票池，并明确股票池的更新时间；
3. 能查看实时或延时行情，页面明确标出来源、时间和延时口径；
4. 能添加、删除自选股，重启后仍然保留；
5. 能查看日 K 线，并至少提供均线、MACD、KDJ、RSI 等已有指标；
6. 当主行情源失败时给出错误和备源状态，而不是展示旧数据或零值；
7. 核心流程有自动化测试，并有一份可重复执行的发布检查清单；
8. AI 分析是可选增强项，不能阻塞基础行情、自选股和 K 线。

## 2. 推荐决策：桌面端优先

### 为什么这是当前最短路径

- 桌面壳、Go 后端、SQLite、Vue 页面、搜索、自选股、K 线和技术指标已经存在；当前工作重点应是验证和修复，而不是重写。
- SQLite 和本地设置天然适合单用户桌面软件，不需要立刻引入账号、鉴权、多租户和云数据库。
- 现有前端大量依赖 Wails Runtime 和生成的 Go 绑定；改成 Web 端需要逐项设计 HTTP/SSE/WebSocket API，不是修改部署配置就能完成。
- 行情准确性与股票池完整性是产品价值的基础。先改部署形态不会自动提高数据质量，反而会同时引入服务运维和安全问题。

### 暂不推荐的方向

- **不建议继续尝试把主 `frontend/dist` 直接部署到 Netlify。**它只能发布静态资源，不能提供 Wails 注入的 Go 方法和桌面 Runtime。
- **不建议第一步重写完整 Web 版。**这会把“验证已有功能”扩大成前后端协议、用户体系、云数据库、密钥管理和运维的联合项目。
- **不建议把 AI 作为第一验收条件。**AI 依赖密钥、模型服务和额外费用；基础股票工具应在未配置 AI 时仍可使用。

## 3. 下一步执行顺序

## P0：得到第一个可运行安装包（1 个里程碑）

目标不是证明“代码应该能运行”，而是产生一个真实用户可以打开的产物。

1. 选定唯一首发平台。若没有明确用户平台，优先选择项目主要开发和现有脚本支持较完整的 Windows。
2. 在该平台运行 `wails doctor`，补齐 WebView、编译器和 Wails CLI 依赖。
3. 执行 `npm ci`、`npm run build`、`wails build`，保留完整构建日志。
4. 在一台未安装开发环境的干净机器或虚拟机启动产物。
5. 验证首次启动、数据库创建、二次启动、异常退出恢复和卸载/便携运行。
6. 把上述步骤放入 CI；在此之前，不把“前端能打包”等同于“应用可运行”。

**退出标准：**存在一个带版本号的安装包或便携包，干净机器冒烟测试通过，并记录操作系统版本、构建提交和测试结果。

## P1：锁定股票数据正确性

1. 对股票基础数据建立统一结构：代码、名称、交易所、板块、上市状态、更新时间。
2. 选择一套权威或可稳定维护的股票清单作为基准，并定义是否包含北交所、科创板、创业板、退市整理及暂停上市证券。
3. 将内置 JSON 的总数、分市场数量、重复代码、空名称和非法代码纳入自动化测试。
4. 为实时行情和 K 线明确主源与备源；记录 `source`、`fetched_at`、`market_time`、复权方式和缓存时间。
5. 选取覆盖上交所、深交所、北交所和不同板块的固定样本，与来源页面或另一独立数据源进行每日对账。
6. 禁止静默降级：请求失败、数据过期、复权口径不一致时必须在界面显示。

**退出标准：**股票池检查可重复执行；固定样本的代码、价格、涨跌幅、成交量和 K 线口径均有对账记录；断网和上游失败不会伪装成正常数据。

## P2：打通最小用户闭环

按照真实使用顺序验收，而不是按照代码模块数量验收：

1. 搜索股票；
2. 查看价格、时间和数据源；
3. 加入自选分组；
4. 重启应用并确认自选仍存在；
5. 打开日 K，切换指标和时间范围；
6. 在行情源不可用时看到可理解的错误；
7. 导出或保存最基本的分析结果。

每一步至少增加一层测试：纯转换逻辑使用单元测试，数据库使用临时 SQLite，数据源使用录制响应或本地 mock，桌面关键流程使用发布前人工冒烟测试。真实网络测试单独标记，不能让默认测试无限等待。

**退出标准：**上述闭环在首发平台连续执行三次无阻断；默认自动化测试不依赖真实外网并有明确超时。

## P3：再决定是否需要 Web 版

只有出现以下明确需求之一，才值得启动 Web 化：

- 多设备同步自选股；
- 无法安装桌面软件的用户需要浏览器访问；
- 多用户共享分析结果；
- 需要集中运行定时任务和行情缓存。

Web 化时应保留 Go 数据层，但新增独立 HTTP API，并把 Vue 中的 Wails 调用逐步替换为可切换的客户端适配器。生产环境还需要账号与权限、服务端密钥管理、PostgreSQL、限流、审计日志、监控和备份。Netlify 可以继续承载静态前端，但 Go API 和持久化数据库应部署到适合长驻服务的平台。

## 4. 建议的首个开发迭代

下一次代码迭代只做以下四件事，避免范围失控：

1. 建立可重复的首发平台构建和启动冒烟检查；
2. 增加内置 A 股股票池完整性测试及统计命令；
3. 为搜索、自选股持久化和日 K 主流程增加离线测试；
4. 在行情结果中统一展示数据源、行情时间和获取时间。

完成这四项后再判断具体功能缺口。若构建或核心闭环失败，优先修复；若它们通过，再做股票池同步、行情备源和分析体验。不要在此之前投入 Netlify 配置、移动端或大规模 UI 重做。

## 5. 已确认的第一版产品边界

产品负责人已确认以下决策：

1. **首发平台：**Windows；
2. **行情时效：**必须接近实时；
3. **股票范围：**上交所、深交所、北交所的在市股票；
4. **证券类型：**包含交易所上市 ETF，不包含场外基金及非 ETF 基金品种；
5. **AI：**可选增强功能，不作为基础功能的启动依赖；
6. **发布形式：**Windows 便携版或安装包，优先先产出便携版以缩短首次验证链路。

### 必须澄清的口径

- “ETF、不包含基金”在分类上存在歧义，因为 ETF 本身属于基金。本文将其解释为：**包含交易所上市且证券类型明确为 ETF 的品种；排除场外开放式基金、普通封闭式基金、LOF 及其他非 ETF 基金品种。**若业务希望包含 LOF，需要另行变更范围。
- “接近实时”不是可直接验收的指标。第一版必须在选定行情服务后，把它改写成可测量的 SLA，至少包含交易时段端到端延迟阈值、统计分位数、可用率、停牌处理和数据源故障时的行为。在数据服务合同或接口能力尚未确认前，不承诺具体秒数。
- “在市股票”暂定为数据源标记为正常上市或暂停交易、但尚未终止上市的股票；退市整理和已退市证券默认排除。新股上市、证券更名、停复牌和终止上市必须通过增量同步更新，不能只依赖随安装包发布的静态 JSON。

### 接近实时行情的准入条件

现有公开 Web 接口和页面抓取可以用于开发验证，但在没有授权、频率额度、延迟说明和可用性承诺时，不能据此声称生产环境满足“接近实时”。行情源进入生产主链路前必须确认：

1. 是否明确覆盖上交所、深交所、北交所股票及交易所上市 ETF；
2. 行情时间戳是交易所时间、供应商时间还是本机抓取时间；
3. 快照或推送频率、并发限制、日调用额度及超限行为；
4. 价格、昨收、涨跌幅、成交量和成交额的单位与精度；
5. 授权条款是否允许在本软件中展示和分发；
6. 主源不可用时，备源是否保持相同代码、时间、单位和复权口径；
7. 客户端必须同时展示 `market_time`、`fetched_at`、`source` 和延迟/过期状态。

上述信息未完成核验时，产品状态应标记为“行情源待验收”，而不是“已支持实时行情”。

## 6. 第一版验收矩阵

| 领域 | 必须通过的检查 | 证据 |
| --- | --- | --- |
| Windows 构建 | 锁定的 Windows runner 能从干净检出生成便携版；安装包可在其后补充 | CI 日志、SHA-256、版本号 |
| Windows 启动 | 无 Go、Node.js 和 Wails 开发环境的 Windows 机器可首次启动、退出和再次启动 | 冒烟测试记录、应用日志 |
| 股票池 | 上交所、深交所、北交所在市股票无重复、无非法代码，并记录同步时间 | 自动化统计报告、异常明细 |
| ETF | 只纳入明确标记为 ETF 的交易所品种，排除约定范围外的其他基金 | 按市场和证券类型统计报告 |
| 行情 | 交易时间内按最终 SLA 持续测量，而不是用单次成功请求代替延迟和可用性验证 | 延迟分布、失败率、主备切换记录 |
| 自选股 | 添加、删除、分组后重启应用，数据仍一致 | 临时数据库自动化测试、桌面冒烟记录 |
| K 线与指标 | 固定样本的时间、开高低收、成交量、复权口径及指标结果可复核 | fixture 测试、数据源对账记录 |
| 故障行为 | 断网、限流、超时、空响应和过期缓存均有明确状态，不展示伪正常数据 | 故障注入测试 |
| AI 可选性 | 不配置 AI Key 时，启动、搜索、自选股、行情和 K 线不受阻 | 无 AI 配置冒烟测试 |

## 7. 实施开始前仍需完成的一项选择

产品范围已足够明确，可以开始 P0 的 Windows 构建工作；但“接近实时”仍缺少可执行的数据方案。下一步应并行评估候选行情源并形成一张对比表，至少记录覆盖范围、实测延迟、授权、价格、限流、稳定性和备用方案。最终选源前可以完成构建、股票池校验和离线测试，但不能完成实时行情验收。

AI 推荐、手动单股分析、七交易日复盘及收藏快照的最新确认口径见 [`ai-recommendation-product-decisions.md`](./ai-recommendation-product-decisions.md)。该文档同时列出了实施前仍需确认的产品参数；未确认的参数不得在代码中隐式写死。

A 股行情候选、开源项目边界、数据源验收实验和 AI Token 成本场景见 [`market-data-and-ai-cost-assessment.md`](./market-data-and-ai-cost-assessment.md)。开源客户端只能作为技术候选，不能替代行情授权与持续延迟验收。
